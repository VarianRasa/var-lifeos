# Var — Hermes Working Rules

## Source of truth
- Treat existing project `.md` files as potentially stale unless the user says otherwise.
- Prefer current code, tests, runtime behavior, and direct user instructions over old roadmap/closeout docs.
- Use docs as historical context only, not binding product direction.

## Product context
Var is a Flutter local-first productivity / life-OS app:

```text
Calendar home → day mindmap canvas → typed nodes → insights / graph / workspaces / sync
```

Core node model includes tasks, kanban boards, plans, notes, journals, habits, goals, links, events, decisions, resources, ideas, questions, contacts, metrics, expenses, bookmarks, routines, and empty placeholders.

## Agentic coding workflow
1. Inspect relevant files before editing.
2. Trace symbols to definitions/usages; do not guess APIs.
3. Propose a small plan before multi-file UI/UX or feature work.
4. Make the smallest useful diff.
5. Preserve user changes; this repo may have many modified/untracked files.
6. Do not commit, push, reset, or delete user work unless explicitly asked.
7. After code changes, run targeted tests and `flutter analyze` when practical.
8. If full validation is too slow, run the narrowest meaningful check and report what was skipped.

## Enhancement strategy
Work page-by-page unless user says otherwise:

1. Calendar / Agenda
2. Day Mindmap canvas + node editor
3. Command Palette
4. Insights
5. Graph
6. Workspaces
7. Settings
8. Backup / Sync

For each page:
- audit current implementation, state/data dependencies, tests, and visual constraints
- identify one focused improvement batch
- implement minimal code
- verify with targeted tests + analyzer
- wait for user review before broadening scope

## Design direction
- Keep dark-first blackboard / doodle / marker style.
- Polish UI/UX with consistency, visual hierarchy, empty/loading/error states, keyboard flow, and responsive layout.
- Prefer existing widgets/tokens (`AppTheme`, `AppColors`, `DoodleShapeBorder`, shared widgets) over new abstractions.
- No new dependency unless there is clear value and user approves.

## Data and architecture
- Respect feature-first layout: `domain`, `data`, `application`, `presentation`.
- Domain code should stay pure Dart where practical.
- Mindmap state changes should invalidate via `invalidateMindmapState(...)` or `invalidateMindmapStateFromRef(...)`.
- Dates should use local-day helpers from `core/utils/date_utils.dart`.
- Local-first Sembast data remains primary; sync/backup layers are adapters on top.

## Planning files
- Keep Hermes-specific current plans in `.hermes/plans/`.
- Prefer new concise plan files over editing stale historical docs.
